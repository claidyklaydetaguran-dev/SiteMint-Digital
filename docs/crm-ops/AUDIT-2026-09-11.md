## Security findings (ranked)

1. **`CrmDiscovery.tsx` bypasses the auth helper** — 6 raw `fetch(API(...))` calls with a local token getter; no `credentials:"include"`, a 401 never triggers the global sign-in redirect, and the `opsContract` guard regex is sidestepped by the `API()` wrapper (the contract passes while violated). Fix: route through `adminFetch` and tighten the contract regex.
2. **Bearer token has no TTL or revocation** and is identical for every login (process-lifetime constant). Cookie sessions fix this but are honored by only 4 of 12 admin route files.
3. **Login rate limiter keys on client-controllable `X-Forwarded-For`** (`trust proxy` unset) — spoofable; behind the Replit proxy the leftmost XFF is attacker-chosen.
4. **~30 CRM GET routes are outside the route-security contract** (it asserts mutating routes only). All verified to carry `requireAdmin` today, but regressions would be invisible.
5. No secrets exposure found in CRM routes; Resend webhook is signature-guarded; Twilio webhooks validate signatures.

## Data-integrity findings

- **No foreign keys** on `crm_activities`, `crm_tasks`, `crm_deals`, `crm_transactions`, `crm_projects`, `crm_messages`, all `helpdesk_*` link columns → orphan rows on delete.
- Lead-sourced proposals embed **invented budget/timeline** (`crm.ts:1843`).
- `CrmLeads` renders a **fabricated "last communication" channel** derived from status alone.
- Signup pipeline `CRM_SOURCE = "AI Receptionist Signup"` is not a member of `CRM_SOURCES`; the `"AI Receptionist"` tag has no registry.
- `CrmSettings` "Save Settings" is a no-op animation; Security and Team sections are hardcoded text; `CrmAdminSettings` is a decorative shell (12 of 14 tiles dead, unconditional "SMS not connected" banner that never consults the real status endpoint).

## Readiness verdicts (denominator = the 28-item inventory above)

Counting rule: **V** counts as ready; **U/P** count as not-ready for the tier that needs them; unknowns count as not verified. Percentages are given only next to their checklists, per instruction.

### Owner testing — READY WITH CAVEATS (19/28 usable: 11 V + 8 P usable-with-care)
The core journey (inquiry → lead → proposal → project → tasks → reporting) is real, persisted, and operable by one person today. Caveats the owner will hit: decorative controls (leads bulk strip, readOnly search, settings save), the unreachable CSV export, stuck spinners on network errors, desktop-only sub-pages.

### Daily internal operations — NOT READY (blockers below)
Critical blockers, independent of any percentage:
1. Single shared identity — no per-staff accounts, so "who owns the next action" cannot be answered truthfully by the system (assignment is free text).
2. No reminder/notification engine — follow-ups exist as data but nothing fires; daily ops would silently miss commitments.
3. Failed background jobs invisible — a receptionist signup whose CRM link permanently fails disappears.
4. Fake/no-op UI misleads operators (settings, admin hub, bulk strip).
5. Error states that strand pages on transient failures.

### Hosted production staff access — NOT READY (blockers)
1. All of the daily-ops blockers, plus:
2. In-memory bearer token: restart logs everyone out; any horizontal scaling breaks login entirely; no revocation of a leaked token short of restart.
3. Cookie sessions (the fix) not honored by 10 of 12 route files, and `crm_admin_sessions` degradation is silent when the table is missing.
4. Rate-limiter XFF spoofability under the production proxy.
5. No password recovery; a lost `ADMIN_PASSWORD` is an ops incident.
6. Unbounded queries (every list fetches every row) — acceptable at current data volume, a time bomb at production volume.

## Integration contract proposal (for the receptionist workstream)

1. **Stable business identifier:** `intake_firms.id` (already the FK on `voice_signup_jobs`).
2. **CRM record identifier:** `crm_leads.id`. **Proposed durable join:** additive nullable `crm_leads.intake_firm_id` column (push-mode table, additive-only) written by the `crm_link` job, replacing the email+notes-string heuristics. Until approved, the jsonb `result.crmLeadId` on the completed `crm_link` job row is the only authoritative mapping and must not be deleted.
3. **Allowed fields (pipeline → CRM):** name, company, phone, email, source, serviceInterest, tags append, notes append. Pipeline must never overwrite operator-edited fields on an existing lead (current behavior complies: tag+note append only).
4. **Status transitions:** the pipeline never changes `crm_leads.status`; CRM staff never write `intake_firms`/voice tables (ops pages are read-only + issue-resolve only).
5. **Retry/duplicates:** `ux_voice_signup_jobs_firm_id_kind` + `onConflictDoNothing` is the dedupe boundary — one `crm_link` per firm ever; CRM-side convert-to-project idempotency via `convertedProjectId`.
6. **Write ownership:** signup pipeline (receptionist session) is the only writer of receptionist-sourced leads' tags/notes; CRM (this session) owns all other lead writes. Neither writes the other's tables. Deduplication remains **email + explicit operator action** — no automatic merging of distinct businesses sharing a contact email.
7. **Reconciliation:** CRM gains a read-only view of `voice_signup_jobs` failures (this session, read-only SELECT in `crm.ts`); retrying/fixing failed jobs stays with the pipeline owner.
8. **Never copied into CRM:** passwords, session tokens, provider credentials, call content.
9. **Staging vs production:** mappings live in whichever database the deployment points at; no cross-environment ID reuse; test rows are labeled (`[CRM-TEST]` prefix) and created only in the isolated local DB.
